# Architecture

`bdetect` is a single-process C++20 offline replay tool with bounded JSON parsing, event extraction, normalization, feature/rule evaluation, and JSONL evidence output. Batch mode loads and normalizes a complete input; `replay --stream` reads one record at a time through a bounded same-second queue and rolling event window. OpenSSL EVP provides rule and dataset SHA-256 digests. There is no kernel collector, live producer service, blocking action, or process-attribution path.

The replay path hashes the rule bytes, hashes the input file before and after parsing, validates event fields, removes exact duplicate IDs, and marks conflicting IDs or late events as unknown evidence. Optional producer session/sequence metadata is scoped by host, source, and session; sequence gaps and collisions, or mixed sequence availability for one host/source, conservatively add unknown coverage. Accepted events are ordered by host/time/ID. Optional pacing maps a separate global event-time timeline to monotonic deadlines; the fast default skips waits. Both modes use the same event-time windows and scoring.

Stream mode opens a regular input file without following a final-component symlink, hashes that descriptor, then reads capped JSONL records from the same descriptor. It requires nondecreasing whole-second event time and rejects producer sequence fields; batch mode remains the path for tolerated reordering and sequence-gap checks. It groups one event second at a time (up to 4,096 records/64 MiB), keeps at most 100,000 active events/64 MiB and 100,000 recent IDs, and drops excess events while retaining an `unknown` issue for the affected host through the event-time window. After scoring each endpoint it releases snapshot copies; active payloads expire from a monotonic event-time index. Output records are serialized incrementally into a mode-0600 sibling temporary file, capped at 512 MiB, synced, and renamed only after the input descriptor's metadata and content hash remain unchanged. Hard-limit, parse, ordering, integrity, and I/O failures remove the temporary file; queue and active-window overflow are handled as dropped evidence with unknown propagation. The mode is single-threaded and offers bounded file ingestion, not asynchronous producer backpressure or watermark-based out-of-order acceptance.

At each distinct event-second endpoint, `evaluate` maintains an overlapping `[end - window_seconds, end]` interval. It counts unique modified, renamed, deleted, and extension features. Versioned rule objects declare feature, comparison operator, threshold, weight, and minimum samples. Each match adds a configured contribution and structured evidence to the decision. A degraded source or insufficient required sample count results in `unknown` rather than benign. As the left edge advances, it releases the string payload of events that can no longer enter a window; event objects and timestamps remain until the batch finishes. Optional `--stats-out` emits a separate replay-stats.v1 sidecar with per-decision percentiles and does not change decision records.

The fixture generator writes harmless event metadata for eight differentiated benign labels and four synthetic suspicious patterns under a caller-provided sandbox. The labels are generated beside the data and are not an independent holdout. Metric output is a pipeline wiring check, not detection-quality evidence.

`evaluate_labels` always writes the existing JSON confusion metrics. Optional `--csv-report` adds the same metrics as rows with explicit numerators, denominators, and values, followed by decision rows sorted by window end, entity key, and start time. Optional `--html-report` emits a static escaped HTML rendering of those metrics and rows. Both optional timelines retain at most 100,000 records; prediction parsing is capped at 1,000,000 records. Neither report includes raw file paths, and the HTML page labels the result as simulation-only. Report generation was added after the last technical verification; its behavior remains unverified.

`analyze-rules` reads decision reason IDs and counts each rule's active decisions and each pair's joint, exclusive, and absent activations. It reports Jaccard similarity and phi correlation in `bdetect.rule_analysis.v1`, with caps of 1,000,000 decision records, 256 distinct rules, and 10,000,000 pair updates. The analysis is descriptive: adjacent overlapping windows are dependent, and the program does not modify rules or weights. This feature was also added after the last technical verification.

`dataset-freeze` accepts separate development and holdout files, a validated rules file, and a new manifest path. It records file sizes, exact SHA-256 values, ruleset revision/hash, split marker, and creation time; the manifest is created without replacement and made read-only. `dataset-audit` compares all three hashes and dataset sizes to that manifest, then appends a locked, owner-only JSONL audit record and syncs it before reporting status. A mismatch is logged and returns status 1. The command does not create or prove the independence of the split, and a local ledger is not tamper-proof against its owner. The freeze/audit implementation and schemas are not technically verified yet.

Resource limits cap each input file at 512 MiB, JSON event lines at 1 MiB, decision lines at 64 MiB, per-decision rule-evidence strings at 32 MiB, total events and evaluated predictions at 1,000,000, rules at 256, host cardinality, labels, and optional report timeline rows. `analyze-rules` also caps pair-update work at 10,000,000. Batch input and normalized copies coexist during loading/normalization; the parsed input vector is released before scoring, and batch event objects/indexes remain until processing ends. Stream state has separate queue, active-window, ID-cache, event, evidence, and output caps. Stream mode rejects out-of-order timestamps and does not finalize producer sequence gaps; a watermark that accepts bounded disorder and attributes gap intervals remains future work. File paths remain present in decision evidence where needed for explainability, so report omission does not amount to repository-wide path pseudonymization.
