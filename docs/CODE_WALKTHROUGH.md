# Code Walkthrough — Linux Ransomware Behavior Detection Lab

## 1. CLI and input evidence

`main` dispatches each command and catches exceptions at the process boundary, returning status 2 on failure. In `replay`, `load_rules` reads up to 1 MiB of JSON, validates the rules.v1 contract, and computes a SHA-256 digest through OpenSSL EVP. The input dataset is hashed before and after parsing; a byte change during loading aborts the run.

`load_events` reads bounded newline records, verifies UTF-8 and required event.v1 fields, parses an RFC 3339 observation time with an explicit timezone, and copies only the event ID, host, kind, path, timestamp, and coverage. Offsets normalize to UTC seconds; a fractional part is accepted but not retained, so window ordering has one-second precision. It caps record bytes, field sizes, and total event count. It intentionally does not infer a process actor.

## 2. Rule validation

`Rule` stores `id`, `feature`, `op`, `threshold`, `weight`, and `min_samples`. `load_rules` allows a bounded number of unique rule IDs, a fixed feature vocabulary, five comparison operators, and integer bounds. Invalid rules are rejected before event scoring. The digest is over the exact file bytes, so whitespace edits also change `ruleset_sha256`.

## 3. Normalization and replay time

`normalize_events` uses IDs to remove exact raw-record retransmissions. A reused ID with different bytes—including formatting-only changes—is conservatively treated as conflicting evidence; a late event also adds a host-level unknown condition. Optional `producer_session_id` and `producer_sequence` must be supplied together. After ID deduplication, records are grouped by `(host, source, session)` and sorted by the numeric sequence, so event-time reordering does not create a false gap. A new session can reset the sequence; a skipped value or two different event IDs using the same sequence degrades host coverage. If only some events from one host/source carry sequence metadata, completeness cannot be proven and the host becomes unknown. A producer with no sequence metadata remains usable under the old behavior, but missing records are unobservable. Accepted events are sorted by host, event second, then ID for window evaluation.

`pace_replay` is optional. It orders event pointers globally and maps event-time offsets to `steady_clock` deadlines. `--speed 0` skips waits; positive values replay at the requested event-time multiple, with a one-hour maximum scheduled wait. The scorer still uses event time only, so fast and paced runs should produce identical bytes. This is a paced offline timeline, not a streaming service that emits live decisions.

`replay --stream` bypasses `load_events` and `normalize_events`. `stream_replay` opens a regular file with `O_NOFOLLOW`, hashes its descriptor using bounded `pread` chunks, and then reads through a fixed 64 KiB buffer. `read_stream_line` retains at most one 1 MiB record, and `parse_event_line` reuses the batch event contract. Producer sequence metadata remains batch-only. The stream tracks the maximum observed event second and derives a watermark from the configured lateness tolerance at the parser's whole-second precision. A bounded map groups queued records by event second and host; timestamps below the watermark are drained in order, while records older than the active watermark are rejected before the output file is committed. The pending queue is capped at 4,096 entries/64 MiB across the open interval, rather than just one timestamp. Excess records are dropped and add a host issue through `event_second + window_seconds`, so later in-window endpoints cannot silently become benign.

When the watermark advances, `flush_endpoint` prunes expired events from `active_order`, admits the timestamp bucket subject to 100,000-event/64 MiB active-window limits, and scores each affected host at that endpoint. Records in a bucket are ordered by event ID to keep output deterministic when the input order differs. The recent-ID index is ordered by event time and capped at 100,000 entries; it expires IDs older than the window plus lateness allowance. `evaluate` receives a bounded snapshot and a single requested endpoint; stream decisions get a monotonically increasing global ID. A dropped-only host still gets an explicit unknown decision. `issue_until` retains a small set of reason deadlines per seen host; producer sequence gaps are not inferred. Watermark additions have not been built or tested.

## 4. Window feature scoring

`evaluate` groups stable pointers by host, then advances a left index across each host's sorted timeline. Each distinct event second is an endpoint; the active interval is `[end - window_seconds, end]`. The right cursor advances once through sorted events instead of rescanning prior rows. Sets calculate unique modified/renamed/deleted paths and extensions. For every rule with enough samples, the engine compares its feature value using the configured operator. A match adds its weight to the score and creates a structured reason with observed value, operator, threshold, weight, contribution, and the exact event IDs that fed that feature. Any degraded evidence or insufficient required samples yields unknown. Once an event falls left of every future window, its owned strings are released; its event shell remains in the batch vector until evaluation ends.

## 5. Output and metrics

`serialize_decision` is shared and escapes every emitted string, including unknown reasons. `evaluate` caps copied rule-evidence IDs at 32 MiB per decision before serialization; the writer separately caps the full record at 64 MiB. Batch `write_decisions` writes decision.v1 JSONL directly. In stream mode, each serialized record is appended through `write_all_fd` to `AtomicDecisionOutput`; the file is mode 0600, capped at 512 MiB, synced, closed, and renamed only after a final descriptor metadata and SHA-256 comparison. Its destructor removes the temporary file on an exception. Stream output is atomically visible after success, though the containing directory is not synced and no power-loss durability claim is made. Optional batch `--stats-out FILE` measures `evaluate` and per-decision scoring with `steady_clock`, then writes a separate replay-stats.v1 record with nearest-rank p50/p95/p99 and max. Stream mode rejects `--stats-out`. `evaluate_labels` parses bounded two-column CSV records, including quoted commas, escaped quotes, and embedded CRLF/LF, then joins by the exact entity key. It reports TP/FP/TN/FN/unknown with rates that use `N/A` for zero denominators and rejects missing/extra prediction entities, duplicate labels, malformed quoting, and invalid labels.

When `--csv-report FILE` is requested, the evaluator retains up to 100,000 compact `PredictionRecord` values. It sorts them by window end, entity key, and window start, then writes metric rows and decision rows with quoted fields and CRLF separators. `--html-report FILE` uses the same bounded timeline and escapes `&`, `<`, `>`, quotes, and apostrophes before inserting values into a static HTML table. These reports omit raw file paths; they contain entity keys, labels, time-window bounds, outcomes, and a score if the decision record has one. Prediction input is capped at 1,000,000 non-empty records. The JSON metrics format remains the default and is unchanged. This optional report implementation has not yet been technically verified.

`explain` scans a decision file for an ID and prints that serialized record. It does not recompute or validate the underlying hashes.

`analyze-rules --input DECISIONS --report FILE` reads only `reasons[].rule_id`, so paths and event evidence are not copied into the report. Per decision it deduplicates active rule IDs, updates marginal counts, and increments co-activation counts for active pairs. It then derives `a_only`, `b_only`, and `neither`, computes Jaccard and phi values, and emits a bounded `bdetect.rule_analysis.v1` report. Pair-update work is capped at ten million operations. Because replay emits overlapping windows, these rows must not be interpreted as independent samples or as proof that one signal causes another. The implementation and report contract are not technically verified yet.

`dataset-freeze` validates the rules through `load_rules`, hashes both separately supplied datasets, rejects identical file/content inputs, and uses `O_CREAT|O_EXCL|O_NOFOLLOW` to create a new manifest without replacing an existing path. It records exact file byte counts and hashes, rules revision/hash, and epoch time, then applies read-only mode and syncs the file. `dataset-audit` parses that bounded one-record manifest, rehashes all inputs, checks the recorded sizes and rules revision, and appends one status record to an owner-only JSONL ledger. `flock` serializes concurrent appenders; `O_APPEND` and `fdatasync` keep each audit record together and request persistence. If a dataset or rules file changed, the mismatch is recorded before the command returns status 1. The ledger is not signed, and the command cannot prove the holdout was independently collected or never used during tuning.

## 6. Fixture sandbox and lifetimes

`generate_fixtures` requires a pre-existing root and a new output directory, then verifies the resolved output is beneath the root before writing synthetic event streams and labels. It creates event metadata, not file workloads. File streams and OpenSSL contexts are RAII-managed.

In batch mode, the input vector owns strings and normalization creates a second owning vector. `string_view` indexes refer to the first vector, and evaluator pointers refer to the normalized vector. After normalization, the input vector is released. During scoring, expired strings are freed while event shells and host indexes remain. Stream mode instead owns parsed event strings in per-host active deques. `active_order` contains only copied host keys and timestamps; when the TTL edge passes an event, the code releases that event's strings, pops its deque shell, and decrements count/byte accounting. A scoring snapshot temporarily copies active events for one host; `evaluate` releases the snapshot payloads before it is discarded, leaving the active deque's originals intact. The bounded ID cache owns each recent ID and raw-line digest until its event-time retention interval expires. `AtomicDecisionOutput` owns the temporary descriptor until commit or cleanup. Requested batch latency stats add and sort one 64-bit sample per decision. Batch memory scales with total event cardinality; stream event state is bounded by the documented queue, active window, ID, entity, and output limits.
